# 内容访问 seam 与图片解析保持解耦

## 背景与决定

我们把分散在 8 个页面与 RSS 路由里的 `queryCollection` 取数收敛成一个**内容访问 seam**（`shared/content/*` 纯核 + `useBlogPosts/useLearnArticles/useProjects` 等适配）。在设计时讨论过是否让内容模块顺带把解析好的封面图（`useArticleImage` 的结果）贴到每条 entry 上，使模板可以直接写 `post.image.src`。

**决定：内容访问 seam 只返回 content entry，不附带图片。** 图片解析留在模板，或交由独立的"图片身份进 frontmatter"改造（见架构审查候选 2）处理。

## 理由（trade-off）

- 内容访问与图片策略是两个**应当独立变化**的关注点：查询/排序/缓存键属于"取数"，封面/署名/比例属于"配图"。把后者塞进前者会让一个 seam 同时承担两件事，测试面随之变宽。
- 让两个候选可以**各自独立推进与回滚**：内容访问 seam 不依赖任何图片策略，图片改造也不必先动取数。
- 内容模块的纯核（`buildSpec`/`relatedPredicate`/`mergeFeed`）保持无运行时依赖、可纯函数单测；一旦耦合 `useArticleImage`（依赖 Vue/Nuxt 上下文），纯核就被污染。

## 后果

- 模板（或 frontmatter 改造后的 entry）继续各自负责图片解析。这是**刻意为之**：未来若有人看到内容 composable 返回的 entry 不带图片，可能想"顺手补上"——请先读本 ADR。把图片并入 entry 需要充分理由（例如图片解析已迁入 frontmatter、`useArticleImage` 不再依赖组件上下文），否则不要重新耦合。
